# Incomplete search results and EOF patch corruption in code tools

**Date:** 2026-11-19 22:32
**Files:** src/lean_weave/executor/models.py, src/lean_weave/executor/source.py, src/lean_weave/executor/patch.py, src/lean_weave/executor/workspace.py, src/lean_weave/executor/approval.py, src/lean_weave/executor/git_diff.py, docs/code-tools.md, tests/config/test_tools_config.py, tests/executor/*.py, tests/verify/test_checks.py
**Severity:** high

## Problem

Verification of the standalone code tools exposed four blocking defects:

1. `search_symbols` returned `complete=true` after failing to read eligible
   candidates. A zero-hit query over a workspace containing an oversized and a
   binary `.py` file returned `omissions=['oversized', 'unsupported']` with
   `complete=true`, making a partial scan look definitive.
2. `apply_patch` concatenated logical lines when a hunk inserted after a final
   line that had no newline. For example, `b"last"` became `b"lastnew\n"`.
3. A final line without a newline could be replaced without the required
   `\ No newline at end of file` marker, silently adding a terminator.
4. Atomic replacement created the temporary file with `os.open(..., mode)`, so
   the process umask narrowed ordinary bits (`0o664` became `0o644`).

Two non-blocking gaps were fixed at the same time: `result_chars_max` was not
applied to search hits or Git entries, and approving tools did not freeze the
effective limits. Hardening also closed two low-risk gaps: a symlinked ancestor
could make the ignore loader stat and open a `.gitignore` outside the root, and
Git repository-config checks used a separate subprocess budget.

## Root Cause

- The search loop treated only `scan_limit` and `indeterminate` as incomplete.
  Every other read failure was appended to `omissions` and the scan continued
  with `complete` unchanged.
- Patch rendering preserved the original terminator of an unchanged final line
  and appended inserted lines without checking that the result still had only
  one unterminated line at EOF. Marker validation only checked markers that
  were present; it never required one for an old EOF without a newline.
- `os.open` applies `umask` at creation time. The snapshot mode was passed as
  the create mode but never restored with `fchmod`.
- `result_chars_max` was only consulted by range reads. Hit and entry lists
  were bounded by counts and raw Git capture bytes, not by the configured
  result budget.
- `ToolsConfig` is intentionally mutable for config loading, and the approval
  snapshot reused that mutable model directly.
- `authorize()` loaded ancestor ignore files before classifying path components,
  so `<symlink>/.gitignore` was resolved through the link first. Git inspection
  also called the context module's fixed-budget config check instead of the
  approval's shared runner.

## Solution

- Search now marks the result incomplete for every candidate read failure and
  uses `scan_limit` as the only case that stops the scan early.
- Patch rendering rejects a missing no-newline marker on a touched final old
  line and rejects any postimage with an unterminated line before the last
  output line. This covers both pure insertions and context-marked forms.
- Replacement calls `os.fchmod` on the staged descriptor before writing and
  `writes_available()` now requires `fchmod`.
- Added `cap_result_items`, which trims repeated result items until the
  serialized envelope fits `result_chars_max` and sets `truncated=true`.
  Search hits, ambiguous candidates, and Git entries use it; `GitDiffSuccess`
  gained a `truncated` field.
- Approval snapshots use frozen `_SnapshotTools` and `_SnapshotCheck`
  subclasses, so field reassignment after approval raises instead of widening
  the policy. Source `AppConfig` objects remain mutable.
- Git admission now treats `scan_limit` and `unreadable` as `incomplete`
  instead of publishing metadata from an unaudited snapshot.
- `authorize()` classifies symlink and non-directory components before loading
  ignore files. Git repository-config inspection now runs through the same
  bounded runner with `min(5, runtime_s_max)` and `capture_bytes_max`, returning
  `incomplete` for a truncated or timed-out check and `unavailable` for an
  unsafe or unsupported one.

## Prevention

- Any scan that reports completeness must fail closed: if a candidate could not
  be inspected, completeness is false even when the hit list is non-empty.
- When transforming line-oriented data, assert the invariant "only the final
  line may omit its terminator" after every edit.
- Preserve metadata with an explicit operation (`fchmod`) after creation; never
  assume the create mode survives the umask.
- Apply every configured result budget to every result type that can grow with
  repository size, and expose truncation explicitly.
- Treat an approval snapshot as data that cannot change after construction;
  freeze copies rather than aliasing mutable config models.
- Regression tests should include oversized/binary search candidates, EOF
  insertion into files without a final newline, group-writable modes under a
  set umask, character-budget truncation, and scan-budget exhaustion.
- Classify untrusted path components before reading any policy file through a
  pathname; keep every child process on the shared bounded runner.
- Test that no Git inspection path reaches unbounded `subprocess.run` and that
  symlinked ancestors never trigger an outside ignore read.
